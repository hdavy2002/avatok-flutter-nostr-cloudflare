# Audit — Fast Call Answering (read-only, no build, no prod write)

**Date:** 2026-08-18 · **Mode:** read-only audit · **Branch:** `main` at `b21e3470` (5 commits ahead of `origin/main`, not pushed) · **Worker:** `worker/src/routes/call_sfu.ts` contains `ExecutionContext`/`waitUntil` path (not yet verified deployed to prod) · **Request:** what's done, what remains, what gets us to WhatsApp parity for audio — slowness only, not quality

---

## What I understand the job to be, in plain English

Today a 1:1 audio call has two slow gaps. First, after the OS notification appears, AvaTOK's own Answer screen takes about five and a half seconds to appear — the user cannot tap Accept during that wait. Second, after the user does tap Accept, it takes about six seconds in a clean call and up to eighteen seconds in the bad trace you flagged before the other side can actually be heard, with the UI already saying "Connected" and the timer running while the user says "hello? hello?" into silence. WhatsApp feels instant because both phones have already done the heavy server work while the phone is still ringing, so Accept is just a state flip. The job is to make AvaTOK the same: Accept to hearing voice in under a second, no blank screen at any point, and the Answer screen itself reachable almost instantly. Video and call quality are explicitly not the focus; speed from Accept to audible voice is.

Your extra constraint for this session is to finish everything first, then do a single production build with all approved flags on, plus any worker deploys or migrations that are genuinely required — but only after the slowness shown in your picture is demonstrably solved, with evidence, not documentation claims.

---

## Baseline that this audit measures against

The breakdown file grounds this in one real production call (`avatok-1204d417`, both sides on build 10569, measured on 2026-08-17). Ring transit is fast at about one second and the OS notification surface is up in thirty milliseconds — that leg is not the problem. The AvaTOK branded answer screen then takes 5.61 seconds (`call_incoming_shown` to `call_branded_fsi_routed`), the callee waits another 2.58 seconds before tapping Accept, the SFU join/publish/pull ladder then costs about four and a half seconds in three sequential server round trips, and first audio in that trace is 11.9 seconds after the callee's `call_connected` (18.2 seconds from Accept in the inflated pre-roll trace, about 6.4 seconds in a clean baseline). The UI today marks "connected" at remote-track arrival, not at audible voice, so the visible timer runs twelve to sixteen seconds early.

## What is done — committed on `main`, not yet in any build on a phone

Seven pieces are code-complete on this branch. Six are client changes that need the build to take effect; two server pieces are already in the worker source and one prior server fix is noted as live in production.

**Telemetry and identity off the media path** (`CALL-STAGE0A-1`). All seven `callSfu*` handlers now thread `ExecutionContext` and every `trackUser`/`emailFor` enrichment is moved into `ctx.waitUntil` so join, publish and pull no longer wait for a PostHog queue send. An in-isolate memo for `emailFor` (60 second TTL, 500 entries) and deterministic per-call sampling scaffolding at rate 1.0 are in place, with errors never sampled. This is the free latency that was added on 2026-08-16 when a blocking analytics `await` was introduced to stop workerd dropping unawaited sends. The breakdown notes this worker as live on `740b9fd8`; the current source contains it, but this audit did not observe a prod deployment confirmation for the exact `b21e3470` source.

**The audio-to-video freeze** (`CALL-VIDEO-FIX-1`, `CALL-VIDEO-FIX-3`, `CALL-VIDEO-FIX-4`, `CALL-VIDEO-FIX-5`, `CALL-VIDEO-FIX-6`, `CALL-VIDEO-FIX-8`). The transport now has a real FIFO negotiation queue with per-operation tokens that are invalidated only by their own timeout or by `dispose`, not merely because something queued behind them. A 15 second per-operation timeout poisons the SFU session before the next queued operation is released, and every later operation fails fast until a verified fresh join via `reconnect` clears the poison. Every serialized body checks ownership after each `await` and before each mutation via `_ownsNegotiation(token)` and `identical(pc, _pc)`, including inside `_doPull` and `_publishVideoImpl`. Aborts are normalised into typed failure details so a poisoned session does not escape as an uncaught `StateError` into the call UI. Hard-coded media-slot assumptions are removed: both the initial connect publish and mid-call camera-on now resolve real mids from `pc.getTransceivers()` by matching `sender.track.id`, with no guessing on failure. The overlapped peer-seat poll (`overlapPeerWait`) remains, and stale remote audio tracks are muted client-side when a repull supersedes them. A separate server fix for stale seat carry-forward across session changes (`CALL-VIDEO-FIX-3`) is described as live in production.

**Caller publishes while the callee rings** (`CALL-PREJOIN-2`, refined by `CALL-PREJOIN-3`). The caller's SFU publish is isolated so that a track arriving during the ring does not assign `_pc`, install `onTrack`, or trip the connect ladder and fake "connected" 7.3 seconds early. The trigger is now authoritative placement success (`notePlaceResult` reachable) rather than the slower FCM ring acknowledgement, so an online callee who accepts quickly does not win the race. The FCM acknowledgement remains as an idempotent backstop and keeps owning reachability and no-answer timing. This is the main fix for "connected, meter running, hello? hello?" because it removes the 3 to 4 second mutual publish wait where each side waits for the other's audio before it can pull.

**Honest user-visible connected state** (`CALL-AUDIBLE-1`, hardened by `CALL-AUDIBLE-2`). The existing `_connected` flag — which stops ringback, starts talk timers, cancels four timers, starts watchdogs and aborts the receptionist — is deliberately left untouched. A later, purely presentational milestone `audibleReady` is added. While `_connected` is true but `audibleReady` is false, the call screen and the minimized pill show "Connecting audio…" and withhold the running timer, and the connection haptic is moved to this later milestone. The breakdown's concern that "first audio proves packets arrived, not that sound left the speaker" is addressed: on SFU and P2P paths the probe now polls `pc.getStats()` for `totalSamplesReceived` (falling back to `jitterBufferEmittedCount`) and requires two consecutive increasing samples, never gated on `audioLevel` so a silent caller still connects. RealtimeKit, which has no `getStats`, uses an audio-track-added event plus a 4 second safety timer, and importantly the RTK provider now splits audio and video evidence so remote video arriving first cannot mark audio audible. A bounded fallback (15 attempts, about 3 seconds) prevents a probe that the platform does not support from leaving a call stuck on "Connecting audio…" forever.

**Native answer surface for the 5.61 second gap** (`CALL-NATIVE-ANSWER-1`, hardened by `CALL-NATIVE-ANSWER-2`). `MainActivity` now paints an interactive native ring screen (caller name, Decline and Accept, 72dp targets, no image assets) synchronously on the `avatok.incoming_call_tap` launch, before Flutter has painted a frame. Accept swaps to the existing passive "Connecting…" overlay and hands the tap to Dart through a persisted pending action. The blind 6 second removal that could tear down the only interactive surface while Flutter was still cold-starting is replaced by a 45 second backstop plus two real removal paths: confirmed Flutter handoff (`onFlutterUiDisplayed`) and a terminal call state pushed from Dart (`clearNativeRingScreen`). The native flag is mirrored to disk (`callnative/answer_flags.json`) by `RemoteConfig.refresh()` and read fail-closed. Telemetry `call_native_ring_shown {ms_from_intent}` is the number that proves 5610 milliseconds down to about a hundred.

**Retirement of the unsafe pre-accept media experiment** (`CALL-PREROLL-RETIRE-1`). The `callPrerollV1` path that acquired the mic muted, built an isolated peer connection, published silently and pulled the caller's audio during the ring — which in one measured call pushed Accept-to-audio from 6.4 to 18.2 seconds and shared one SFU session id between two peer connections — is now sealed shut. `RemoteConfig.callPrerollV1` is hard-wired to `false` on the client, and `CallPrewarm` is gated so it cannot execute that extension even if the server flag were flipped. The server key is kept for old-build rollback compatibility. This directly addresses the `session_not_owned` 403 path seen in lowside traces where a closed seat was handed back to the normal answer path.

**Visible video upgrade state.** `CallSession.videoUpgrading` is no longer a wired-but-not-rendered notifier. The call screen now derives its status line from it (showing "Adding video…") and the Video tile shows "Adding…" and disables repeat taps while negotiation settles. The optimistic `call_sfu_video_upgraded` event is retired in favour of `local_video_published` through `remote_video_first_frame`.

The current working tree has one uncommitted change: `app/lib/features/avatok/call_screen.dart` adjusts `_connectedLabel` ordering and the Video tile label/active logic to surface `videoUpgrading`. This matches the branch history but has not been committed.

## What still needs to be done before a single production build is justified

No device has run any of the client pieces. The branch is five commits ahead of `origin/main` and unpushed, and the picture you attached still shows the starting point. The remaining work is therefore verification and a small number of hardening items that a two-device trace will either clear or force back to code.

**Prove the native answer removes the 5.61 second wait under process death and slow engine.** The disk persistence now exists (`pending_ring_action.json` with atomic tmp-then-rename, `nonce`/`timestampMs`/`expiryMs`, 60 second TTL, idempotent `drainPendingRingAction` that clears both memory and disk, and expiry handling that logs `call_native_answer_expired` and `call_native_answer_restored`). What is not yet proven on device is: warm, cold, locked-phone and process-killed incoming paths; that `_brandedRouteGate` prevents a duplicate branded screen stacking on top; that the 45 second failsafe does not trap the user and that `clearNativeRingScreen` from Dart reliably clears a screen that is up while Flutter has not yet painted; and that `ms_from_intent` and `msFromScreenShown` actually land in PostHog. This is the first gate for your picture.

**Prove Accept to playout is no longer the slow path, and that the slow recovery path is gone.** Caller pre-publish should remove the mutual wait, and join pre-warm during the ring should remove the 1.8 second join — but the 12 to 16 second trace that also showed SFU fallback and transport recovery immediately before audio proves pre-publish alone is not sufficient. Two things must be measured on the same trace, not asserted: that `session_not_owned` no longer appears after the preroll retirement and poison-session hardening, and that fallback and reconnect storms no longer add seconds. The instrumentation to do that exists (`call_sfu_*` stage `elapsed_ms` versus `sfu_ms`, `call_audible_ready {evidence, ms_from_connected, ms_from_start}`, `call_prejoin_published`, and per-stage timings from Accept tap through Dart receipt, server accept, mic publish, remote track, first decoded sample and confirmed route). They need to be read on a real staging or production call before the build is declared to solve the picture, and the fallback/recovery investigation needs to move from "instrumented" to "identified and removed" where the cause is avoidable.

**Move the callee pre-warm to the earliest ring ingest, or prove the current siting is early enough.** The breakdown records that the first pre-warm attempt hooked the wrong ring lane and never executed, and the second hooked the branded screen's `initState` — which fires 5.4 seconds late and leaves only about 2.6 seconds of head start before Accept. The spec's P1 calls for moving this to the earliest common ring-ingest point before any UI decision, join-only, with no mic. The current branch's `CallPrewarm.start` wiring should be audited against FCM-isolate handoff and the InboxDO WebSocket ring lane to confirm it actually gets the five seconds the spec expects.

**Path-specific audio-route readiness and platform fallback.** The audible gate now correctly uses playout counters on SFU and P2P and audio-track evidence on RealtimeKit, but the audit noted that route readiness is treated as satisfied by construction once `CallAudioController` has run at boot. That matches reality today — the controller runs before ICE and before `onTrack` — but the reviewer asked for explicit per-path fallback behaviour for RealtimeKit, unsupported platforms and disabled audio-controller flags so that no legitimate call can remain on "Connecting audio…" forever. The 4 second RTK timeout plus the 15-attempt bytes fallback already provide that safety, yet the call-screen copy and the minimized pill should be walked on device to confirm no path can stall the label indefinitely.

**Seal the last negotiation gaps, then re-audit the incoming and audio-to-video path end to end.** The token is now threaded through `connectPublish`, `connectPull`, `publishVideo`, `_connectPullImpl`, `_publishVideoImpl` and `_doPull`, with eight ownership checks and poison set before the queue releases. The remaining audit ask is to walk every remaining shared mutation after an `await` — including the initial publish mid-resolution and `setRemoteDescription`/`setLocalDescription`/`renegotiate` in `_doPull` — and to prove that late work from an old session cannot close or mutate its successor after `reconnect` mints a new session. The separate concern about late work closing a successor connection is now gated by `identical(pc, _pc)` and `_liveTokens`, but a line-by-line pass is still the right gate before paying for CI.

**Separate local video publication from pulling the peer's video where it still couples.** The transport now awaits `_doPull('video')` inside `_publishVideoImpl` rather than fire-and-forget, and the session no longer pulls the peer inside the same serialized slot that published. That satisfies the review ask to not roll back a successful local publish on a peer-pull failure. The remaining device gate is 100 repeated audio-to-video transitions with zero freezes and `local_video_published` through `remote_video_first_frame` observed, plus P95 video-upgrade timing.

**Health telemetry at scale.** Deterministic per-call sampling, unsampled health counters and 100 percent error capture with rate limiting are described as the intended production posture. The mechanism at rate 1.0 is in the worker source; turning it down later must keep the invariant that a missing event still means "code did not run" — the inference that caught three dead features this week. Nothing here blocks a first production call, but the counters that let you keep that inference at one million calls per minute should land before sampling is reduced.

**Backend and flags before the one build.** No D1 or Durable Object migration is evidenced as required for these changes — call state is per-call DO memory and the SFU seat registry is ephemeral — but that must be explicitly confirmed by diffing changed Workers, Durable Objects, config entries and schema dependencies, then deploying changed backend components to staging first and verifying APIs, tests and backward compatibility without producing a staging app build. Only then should the approved fast-call flags be turned on in staging and verified. The approved production set for the final release is narrow: `callSfuV1=true`, `callFirstAudioProbeV1=true`, `callPrewarmOnRingV1=true`, `callerPrejoinOnRingV1=true`, `callAudibleStateV1=true`, `callNativeAnswerV1=true`, with `callPrerollV1=false` and `callRealtimeKitV1=false` left off, and every component retaining an independent kill switch so any one can be disabled without a rebuild. The current local `DEFAULTS` still ship those flags false, which preserves the "ship dark, enable after baseline" staging plan and requires explicit KV flips before the prod build's behaviour changes.

**Final source and compile-risk audit, clean history, one build.** Before paying for GitHub Actions, the repo needs a straight read of native Android manifests and method-channel contracts, Dart analysis, and dependency pins (`flutter_webrtc` 0.12.5, `posthog_flutter`, `flutter_callkit_incoming` 2.5.8), then separate commits per issue through `scripts/git_safe_commit.py`, a Graphify and Graphiti update, `git fetch` and a clean push with no unrelated files or manifest rewrites. Only then should the repository's canonical single production Android release workflow run once — signed APK and AAB, Play Internal publication, build-pointer update and FCM broadcast — with the workflow URL, build number, artifacts, Play result, pointer result, backend versions, migrations and effective flags recorded.

## What I would do to make this feel like WhatsApp

WhatsApp's speed is not a faster server; it is that both ends are ready before the user decides. The pieces already on this branch are the right shape for that, and three of them carry almost all of the perceptible gain.

First, the native answer screen is the largest single win. It does not make media faster; it makes Accept exist. Painting caller name plus Decline and Accept synchronously on the incoming-call tap, with the tap persisted to disk so a process death between the native tap and Dart's drain cannot lose it, is what turns "I pick up, then the screen has no UI of AvaTOK" into "as soon as I pick up I can act." That is why the picture cannot be declared solved until `call_native_ring_shown` shows about a hundred milliseconds on a cold start and a process-killed retest still routes to `PushService.acceptRingingCall` exactly once.

Second, the caller's early publish is the largest media win, but only because it is done safely. Publishing the caller's audio while the callee's phone rings, gated on placement success so the seat write cannot 403, and with an isolated peer connection that withholds `_pc` and `onTrack` until promotion, is what removes the 3 to 4 second mutual wait that produced "I see the meter started, I keep saying hello and hello, then the voice comes." The evidence that this worked is not "no error" but `call_prejoin_published` before Accept and, on the callee, `call_sfu_pulled` finding a live track immediately.

Third, moving the callee's SFU join into the ring — join only, no media, no mic — is the quiet win that the user never sees as a feature but feels as a shorter Accept-to-voice. The 1.8 second join is the one server phase that can always be removed without touching audio privacy, and its value doubles when the native screen gives it five seconds of head start instead of two and a half. The lurker WebSocket idea (a `?prewarm=1` mode that connects to `CallRoom` during the ring without being announced as a peer) is deliberately deferred; it saves about half a second and touches shared signalling, so it should only be built if the first three still leave a measured gap.

Fourth, the honest audible state is what makes the product feel truthful rather than merely fast. Leaving `_connected` meaning "media path established" and adding `audibleReady` for "you can actually hear them" — with real playout counters and a bounded fallback — is what replaces "it says connected but no voice is flowing" with "Connecting audio…" until sound has genuinely left the speaker, and what explains the twelve to sixteen second lie that today's `call_audible_ready {ms_from_connected}` measures. That change is also the only one that touches what the user reads, so it is the one that most needs a flag.

None of this works if negotiation can still corrupt itself. The FIFO queue with per-operation tokens, poison on timeout before the queue releases, and normalised aborts is what prevents the other family of slowness — fallback and recovery churn that made a 6.4 second baseline into 18.2 seconds — from silently returning. Retiring pre-roll is part of the same thought: a second SFU session per call and pre-pull during the ring are not worth the privacy and cost risk until a native fail-closed playout gate is proven, so the branch correctly keeps `callPrerollV1` off.

If that native screen, that caller pre-publish and that join pre-warm are proven on two real devices, and the poison and mid-resolution hardening hold, the remaining Accept-to-voice path is essentially pull plus playout — about one to one and a half seconds — and Accept itself is reachable in about a hundred milliseconds. That is the WhatsApp shape. The last half second, if it is still needed, is then a surgical change like WebSocket pre-warming, not another broad media refactor.
