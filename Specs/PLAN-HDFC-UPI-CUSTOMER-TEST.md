- `worker/src/lib/hdfc_sms_smoke.ts` createIntent, claimStatement, matchIntent and publicIntent already provide the required v2 financial authority: receiving-account single-active index, exact 12-digit payer reference, canonical unique receipt, recovery horizon, fail-closed evidence conflict and read-only GETs. Reuse these claims without restoring commercial HDFC.
- `provisionCommercialPurchase` in `worker/src/routes/commercial_checkout.ts` writes orders, real bookings, availability, entitlements and calendars. Do not call it for this test. Persist a separate test-booking record linked to the existing smoke intent; derive confirmation from its persisted receipt.
- Existing `/test/upi` controller is an admin diagnostic surface. Preserve its island/controller/tests; move its Astro mounting page to `/test/upi/admin`. Make `/test/upi` the invited customer page, including a helpful ordinary sign-in/invitation message when no invite is present.
- Existing `analyticsCore.ts` only redacts /j/ tokens; Base initializes pageview capture. Fragment invitations therefore require URL-property redaction and replay/autocapture exclusion before launch.
- Graphify was consulted first; no Graphiti tool is exposed to this worker. No current PostHog result is an implementation prerequisite.

## Data contract (DB_META, one additive migration)
Create `worker/migrations/2026-09-18-hdfc-customer-test.sql`. Leave v2 seed/readiness view and historical data untouched.
1. `hdfc_sms_test_invites`: invite_id TEXT PRIMARY KEY (UUID); token_hash TEXT NOT NULL UNIQUE (64 lowercase hex); created_at INTEGER NOT NULL; expires_at INTEGER NOT NULL CHECK(expires_at>created_at); bound_uid TEXT NULL; redeemed_at INTEGER NULL; CHECK((bound_uid IS NULL)=(redeemed_at IS NULL)). Index bound_uid,created_at.
2. `hdfc_sms_test_bookings`: booking_id TEXT PRIMARY KEY (UUID); invite_id TEXT NOT NULL UNIQUE REFERENCES hdfc_sms_test_invites(invite_id); intent_id TEXT NOT NULL UNIQUE REFERENCES hdfc_sms_smoke_intents(intent_id); uid TEXT NOT NULL; service_id TEXT NOT NULL CHECK(service_id='upi-demo-consultation'); created_at INTEGER NOT NULL; test_mode INTEGER NOT NULL DEFAULT 1 CHECK(test_mode=1). Index uid,created_at. Fixed service metadata lives in code: 'Demo consultation', 15 simulated minutes; amount 100 paise INR comes from linked intent, never request data. No actual appointment time, provider or real entitlement is implied.
There is no mutable paid/confirmed bit. The persisted booking row and persisted receipt claim together are the confirmation authority. Project customer booking.status from publicIntent: confirmed -> confirmed; review_pending -> review_pending; expired -> expired; pending -> awaiting_payment; superseded -> unavailable. confirmed_at is claimed_at only while receipt disposition=accepted and publicIntent status=confirmed. A later evidence conflict MUST demote the displayed booking too. booking_id is a stable reference before/after confirmation.

## Authorization and invitation lifecycle
All customer routes require an Authorization Bearer header then ordinary requireUser/isFail (canonical account uid and ban gate). Never requireAdmin, accept guest JWT, accept uid from body, or use query-string Clerk tokens. Missing/malformed bearer -> 401. Return private,no-store on all customer API responses and page; page noindex/no-referrer.
Generate 32 cryptographically random bytes as 64 lowercase hex. Persist SHA-256 of the token only. Link format `<approved-web-origin>/test/upi#invite=<token>`; no token in query/path, SQL, analytics, error strings or server logs. Bounded redeem POST carries raw token in JSON exactly once per attempt. The unguessable invite_id becomes the non-secret resume handle after redemption.
Redeem atomically UPDATE invite bound_uid/redeemed_at WHERE token_hash matches AND bound_uid IS NULL AND expires_at>now. Then SELECT by hash and authenticated uid: same uid retries return the same invite even after initial redemption expiry; a different uid/invalid/expired-unbound token gets the same 404 invite_unavailable. First authenticated redemption wins; this intentionally needs no brother email. Binding grants only this test, no admin status.
Invitation expiry (24h default) blocks initial redemption and first order creation. It never blocks reading or recovering an existing payment by its bound uid; existing v2 recover_until remains the claim limit. No invite replacement/revocation feature needed for this bounded task.

## Exact API surface
Add `worker/src/routes/hdfc_sms_customer_test.ts`, supporting helpers in `worker/src/lib/hdfc_sms_customer_test.ts`, and six dispatches/import in worker/src/index.ts. Prefix `/api/pay/hdfc-sms/customer`:
- POST /redeem `{invite_token:string}` -> `{ok:true,account_id,invite_id,expires_at}`. Rate limit by authenticated uid before lookup. Do not return raw token/hash/bound uid of another account.
- GET /current?invite_id=UUID -> `{ok:true,protocol_version:2,account_id,enabled,reason_code,invite:{invite_id,expires_at,can_create},service:{id:'upi-demo-consultation',title:'Demo consultation',duration_minutes:15,test_mode:true,amount_paise:100,currency:'INR'},intent:SmokeIntent|null,booking:TestBooking|null}`. Enforce bound uid. No invite parameter: return latest bound invite for this uid or 404 invite_required (allows resume after reload/account sign-in without browser storage). GET never matches or writes.
- POST /order `{invite_id,service_id:'upi-demo-consultation',request_key:UUID}` -> same current envelope. Bound invite and exact service only; reject arbitrary listing/amount/currency/replace_intent_id rather than implementing them. Existing booking for this invite returns identically before checking expiry/rail enablement, and does not create a new QR. Request key is stable across uncertain response retries; invite uniqueness also prevents duplicate creation across tabs/reload.
- GET /status?invite_id=UUID&intent_id=UUID -> same current envelope, only if booking joins both ids and authenticated uid. No legacy/admin fallback; mismatch -> 404. GET read-only.
- POST /claim `{invite_id,intent_id,bank_reference,expected_reference_revision}` and POST /recheck `{invite_id,intent_id}` -> same current envelope. Enforce bound invite + booking owner + exact intent before saveReference/matchIntent. Keep exact reference/revision validation, enabled policy, recovery and throttles from existing claim route. Never match by amount alone.
Response TestBooking `{booking_id,service_id,service_title:'Demo consultation',duration_minutes:15,test_mode:true,status,created_at,confirmed_at:number|null,amount_paise:100,currency:'INR'}`; no UTR/raw SMS/customer email/secret in response. publicIntent supplies protocol-v2 intent and null order_id. Override only the customer UPI note to 'AvaTOK test booking' while preserving QR identity/amount/payee and all status/eligibility logic.
Use generic 404 for ownership failures, 400 invalid inputs, 409 intent_busy/reference_conflict, 429 throttle, 503 schema_not_ready/rail_paused/configuration_incomplete/storage errors. Expose machine error codes so customer copy explains busy vs reference conflict vs invitation unavailable. Readiness explicitly probes both new tables before customer writes; old v2 admin ingress remains independent.

## Atomic QR + booking creation
Implement a dedicated createCustomerTestBooking helper; do not loosen existing createIntent/admin replacement semantics. In ONE db.batch: (1) deactivate expired active intents for the receiving account as existing helper does; (2) INSERT new smoke intent SELECT with fixed amount/timing, generated id, authenticated uid/request_key, only if bound invite is unexpired, no booking for invite, no active intent for account, and no existing uid/request_key; (3) INSERT test_booking SELECT only the newly generated intent joined with the same still-eligible invite and uid; require no existing booking for invite. A failed constraint rolls the complete batch back. Read booking by invite+uid afterward; return its existing/new envelope or 409 intent_busy. Existing same-uid admin QR is not adopted, replaced or superseded. Active QR from ANY invite/account causes busy, with no disclosure of its id/customer. The partial unique active index is the final concurrent-create guard. Duplicate request keys belonging to another invite cannot attach that intent.
Customer has one booking/intent per invite, no replacement and no 'pay again' action. Expiry hides QR and retains same-payment recovery; another test requires an explicitly issued new invitation. Creation of a booking row does not mean payment confirmed. SMS ingress already selects customer intents and calls shared matchIntent; customer polls subsequently read the resulting joined confirmation. No new matching or finance authority.

## Acceptance criteria — tests in GitHub Actions only
AC1: Ordinary signed-in nonadmin redeems and completes own invited flow; unauthenticated/guest/headerless access rejected; no invite cannot create; all original admin-only route tests still pass.
AC2: Two concurrent different uid redemptions yield exactly one bound uid; same-user retry yields identical invite; expired unbound, malformed/unknown token and other-user resume are inaccessible; no other-account payment/booking fields returned.
AC3: Competing invite creates (including same uid) and admin-vs-customer create produce exactly one active QR; loser gets busy and no booking/orphan; no superseded_by mutation. Concurrent/retried same invite returns same intent+booking; foreign request-key collision cannot attach another intent. Force booking INSERT failure and verify intent creation rollback using real SQLite fixture.
AC4: Existing duplicate-SMS/exact-reference/nonce/revision/recovery invariants retained. Receipt before reference and reference before receipt both produce the same single persisted test booking confirmation. Duplicate ingest/claim/recheck/reload cannot duplicate booking. Amount-only, wrong reference, outside-window, paused rail, unsupported reference and legacy evidence never confirm it.
AC5: GET current/status performs no mutations. Persisted receipt conflicts demote a previously confirmed booking view. No orders/bookings/calendar/entitlement/wallet/escrow/commercial operations created; hdfc gateway remains unregistered and legacy refund remains manual_external_review.
AC6: Browser signed-in customer sees demo selection, real ₹1 disclosure, QR/deep-link, reference form and stable test-only confirmation; reload resumes without extra order POST. Expiry hides QR; status cannot be overwritten by stale response after account/session change. Busy/reference conflict/auth failure messages are distinct; receipt review hides confirmed-booking wording.
AC7: Raw invitation never appears in request URL, referrer, PostHog payload, replay, raw SQL or stored DB row. Successful redemption scrubs fragment, token memory and raw input; only invite id remains. Signout/account switch clears ephemeral state. Test QR generation errors visibly retain the valid deep link/recheck controls.
AC8: Issuance script synthetic tests stub subprocess only, assert wrapper invocation/environment gating, 32-byte token, SHA-256-only DB payload, permissions and no output artifact on failed/unverified insertion. Existing v2 seed tests unchanged. All new CI steps and existing safety workflow pass; no local verification/builds run.
AC9 (root live acceptance after authorized rollout): final shareable fragment link is generated and delivered. Opening its page is customer-facing, ordinary sign-in works without admin assignment. Do not redeem the user's invitation as the operator or fabricate bank evidence/payment. Actual brother payment/booking confirmation remains pending until he performs the real ₹1 transaction and submits its bank reference.
