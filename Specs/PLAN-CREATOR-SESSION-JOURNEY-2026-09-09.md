# Implementation plan: creator-to-customer session journey

Status: proposed implementation plan, 9 September 2026. Production is the intended target; this document does not authorize deployments, builds, purchases or customer emails. Based on AUDIT-CREATOR-SESSION-ACCESS-2026-09-09.md. Recheck affected code and deployed revisions at implementation start because this is a shared repository.

## 1. Product outcome and sidebar placement

Fit the tools inside the existing Marketplace expansion in the supplied app screenshot. Keep the current visual design and top-level profile, Marketplace, Messenger, Library, Wallet, Account & settings and Log out. This supersedes the audit's suggestion of a separate top-level Creator Studio.

```text
Marketplace ▾
  Browse
  My Tickets & Appointments
  CREATOR TOOLS                 ← section label, not another accordion
  Create listing
  My listings
  My Live Events
  Customer Appointments
  Availability
  Archived
```

“My Tickets & Appointments” always means sessions this account purchased/booked. “My Live Events” means broadcasts this account hosts. “Customer Appointments” means appointments customers booked with this creator. A creator who buys from another creator sees both sides. Keep Create listing discoverable to new creators; show operational creator tools when the account has creator activity/eligibility, without requiring a paid subscription. Server authorization remains mandatory regardless of menu visibility.

Show a small Live now/due-soon count on Marketplace and the relevant child destination. Counts and rows must come from the same account-scoped authority. Use one scrollable sidebar; long labels wrap and text scaling must not hide actions. Preserve expanded state per account. Match destination names on web, within its existing navigation layout.

## 2. Journeys to deliver

- Creator event: Marketplace → My Live Events → exact event → Test camera/microphone → private backstage → explicit Start live → live controls → End event. Opening the menu or camera preview never broadcasts.
- Creator appointment: Marketplace → Customer Appointments → exact customer/date/time → preview camera/microphone → Start/Join appointment. The other participant can wait in the room; no automatic selection of an old booking.
- Customer: purchase/booking completes → durable ticket/appointment appears immediately → confirmation email and calendar invite are queued → open email OR Marketplace → My Tickets & Appointments → Watch event / Join appointment.
- Without app: link opens browser → email-code sign-in using the purchasing identity when needed → exact booked destination → join. No mandatory download, subscription or second purchase. Offer account switching if the wrong account is active.
- With app: verified link opens the exact event/appointment after cold or warm launch; preserve the destination through sign-in/account selection. If app opening is unavailable or declined, provide an explicit Continue in browser route that does not loop back into the app.
- Notifications, calendar links, confirmation buttons, listing owner actions and the sidebar must converge on these same screens and server admission checks.

## 3. Ordered implementation packages

### JOURNEY-01 — shared booking IDs and admission contract (critical; first)

Repair worker/src/index.ts and worker/src/routes/commercial_stream_sessions.ts so all consultation prejoin/join/state/end/extension routes accept existing 83-character booking IDs. Use one validated ID contract for router and handler; retain existing stored IDs. Check provider call/channel ID constraints against current primary documentation before changing provider identity generation. Add a router-level test starting with an ID actually generated by commercial checkout, rather than only short synthetic IDs. Align prejoin response fields, including names and join opening/closing times, with both clients.

Done: creator and buyer can reach admission with a real checkout-generated ID; wrong account, unpaid/refunded entitlement, cancelled session and closed window are refused for the correct reason. Existing live admission is unaffected.

### JOURNEY-02 — account-scoped customer and creator schedules

Extend the current commercial sessions projection compatibly: customer view retains viewer/buyer semantics; add a creator view sourced from owned live listings and creator bookings. Include hosted events before any room/host entitlement exists. Return stable product IDs, role, title, counterparty where authorized, time/window, lifecycle state and allowed actions. Add cursor pagination and upcoming/live/past filters; do not silently truncate the operational schedule. Define deduplication so joins to receipts/orders do not repeat a session. Keep provider credentials out of list responses; join endpoints remain the final authority.

Primary files: worker/src/routes/commercial_stream_sessions.ts; app/lib/core/commercial_sessions_api.dart; app/lib/core/listings_api.dart. Replace the past-first selector with explicit booking selection. Creator views sort actionable sessions first and upcoming chronologically; past sessions have a separate view. Refresh on resume, notifications, reconnect and join-window transitions using server time.

Done: a customer sees every purchased ticket and appointment; a creator sees events with zero tickets and every customer appointment, with the correct Start/Join/Rejoin/Ended action.

### JOURNEY-03 — one destination across email, web and app

Canonical public paths: /live/:listingId and /session/:bookingId. Preserve existing /j/:token and query-style app links. Fix joinInfo/web resolver field mismatch; use a typed destination response with stable IDs and product kind. Resolve old commercial /consult links to the commercial room while preserving any genuinely legacy booking behavior. Change checkout confirmation and web TicketCard links. Update Dart path parsing, shell routing, Android verified links and supported iOS associated domains; validate exact allowed hosts rather than suffix matching. Maintain browser recovery for app links and expired invitations through authenticated My Tickets & Appointments.

Primary files: worker/src/routes/booking.ts; worker/src/cal/ics.ts; web/src/lib/urls.ts; web/src/pages/j/[token].astro; web/src/pages/consult/[booking].astro; web/src/islands/checkout/Confirmation.tsx; web/src/islands/dashboard/TicketCard.tsx; app/lib/core/deep_links.dart; native link configuration.

Done: all supported link shapes preserve the exact booking/event and purchasing account through sign-in; forwarding a link never grants paid access to another account. Valid old invitations keep working.

### JOURNEY-04 — durable confirmations, reminders and notification links

Wire every successful commercial fulfilment path (wallet, external payment and free reservation) to a durable notification outbox after entitlement creation. Use stable order/recipient/message-version keys; payment callback retries must not charge again or duplicate mail. Store enough to recover a crash between entitlement creation and enqueue. Distinguish queued, provider accepted, delivered, failed and bounced; recover stale sending leases. Verify Brevo delivery callbacks and reconcile retryable failures. Checkout copy must reflect the known state, not promise an email was delivered when it was only queued.

Send ticket/appointment confirmation to the customer and booking notification to the creator, with exact destination and calendar attachment. Support live tickets without inventing booking rows. Use local time with timezone and a UTC fallback. Provide rate-limited Resend confirmation to the account's verified address. Reschedules/cancellations update messages and calendar sequence without reviving an invalid entitlement. Respect the existing reminder cadence; implement missing live-ticket email reminders and do not mark failed sends complete.

Preserve allowlisted commercial type, listing_id, booking_id/session_id, title and body through worker/src/notify.ts → Q_PUSH → consumers/src/fcm.ts → app notification handler. Pagination must reach all eligible attendees, beyond the current 200-recipient cap, without duplicate notifications. Never include provider tokens in notification data or analytics. Primary files: commercial_checkout.ts, commercial_lifecycle.ts, cal/emails.ts, commercial_notifications.ts, notify.ts, consumers/src/calendar.ts and consumers/src/index.ts.

Done: a real purchase produces one correct confirmation, retry/resend works, both inbox and app notifications reach the same session, and provider delivery evidence is visible to support.

### JOURNEY-05 — app Marketplace tools and customer/creator screens

Add named destinations to AvaSidebar and the shell destination/selection handlers used in both shell modes. Rejoin a live host's controls rather than trying to create another broadcast. Move current listing shortcuts to these same destinations; remove past-first selection. Availability opens the existing availability editor without granting calendar access to another account. Keep browsing/listing management separate from session operation. ### JOURNEY-06 — web parity and browser creator camera controls

Replace the web booking-only list with the commercial customer projection, including live ticket entitlements. Repurpose creator live/consult dashboard pages into My Live Events and Customer Appointments; retain listing administration under My listings. Reuse ConsultRoomGS for both parties and fix its prejoin contract and lifecycle/error recovery. Build the missing browser livestream host console: device preview/selection, camera/mic permission help, backstage, explicit Start live, authoritative live status, reconnect and End. Use the existing server prepare-host/go-live/end API; never mint provider call IDs in the client or create an alternative media room.

Keep viewers receive-only. Show Waiting for creator, Starting, Live, Reconnecting, Ended and access-refused states. Release camera/microphone on leave and failed joins. Reflect server/provider lifecycle confirmation rather than treating an HTTP authorization response as proof video is playing. Preserve browser audio autoplay handling through an explicit join/play interaction. Revalidate expiring auth/provider credentials for supported session lengths without leaking them across accounts.

Done: browser creators and customers can complete both live-event and 1:1 journeys, including mixed app/browser pairs, with correct camera ownership and session ending.

### JOURNEY-07 — support visibility and repair of existing purchases

Instrument the connected journey: purchase fulfilled → email queued/accepted/delivered/failed → link resolved → sign-in completed → admission authorized/refused → creator live → first remote video/audio → reconnect/end. Correlate order, listing, booking, account role, platform, release and failure reason; use verified account email for authorized support retrieval and phone only if already available under existing policy. Never report an audit, API grant or page open as successful media delivery. Link support diagnostics to receipts and delivery attempts.

Inventory existing commercial orders/entitlements and identify affected missing emails, invalid link destinations and missing creator grants. Prepare a reviewable reconciliation report before any production repair. Preserve purchased IDs, amounts and refund state. Any backfill/resend must be explicitly approved, bounded and idempotent; no unsolicited bulk customer email. No new telemetry seeding is needed merely to make dashboards appear populated.

Done: support can explain a failed journey from the purchase to the failing step and retry delivery safely. Existing customers are covered, not only newly created test bookings.

## 4. Dependencies and review structure

Implement JOURNEY-01 first; then JOURNEY-02/03 contracts, JOURNEY-04 delivery, JOURNEY-05 app navigation, JOURNEY-06 web parity, and JOURNEY-07 reconciliation/operational completion. Add observability and relevant tests with each package rather than waiting until the end. Reconcile shared-tree edits before changing the sidebar. No local builds/compiles/analyzers; meaningful verification executes in authorized CI or approved device/browser sessions.

## 5. Acceptance matrix — required evidence, not optional polish

| Scenario | Required result |
|---|---|
| Creator app → customer browser, event and 1:1 | Exact purchased session; remote video/audio; correct end state |
| Creator app → customer app, event and 1:1 | Same authority and media, recovered from Marketplace menu |
| Creator browser → customer app, event and 1:1 | Browser host works; attendee uses same session |
| Creator browser → customer browser, event and 1:1 | No app installation; device permission and email-code login work |
| One live event, at least two independent paid customers | Both join the same host broadcast with independent entitlements |
| Creator with past, current and multiple future appointments | Each button opens its exact booking; current action never selects past |
| Email on fresh browser; app cold/warm launch | Destination survives authentication; no app-opening redirect loop |
| Wrong account, forwarded link, cancelled/refunded order | Access refused with recovery guidance; no extra charge |
| Duplicate payment callback; crash/retry; missing/bounced email | One entitlement; bounded retries; accurate delivery status |
| Early arrival, host absent/late, disconnect, token expiry, ended room | Truthful state and safe retry; existing money/no-show policy preserved |
| Purchase made before these fixes | Correct retrieval, join and approved resend without re-purchase |
| Shared device/account switch | No other account's tickets, names, cached session or credentials |

Use production-shaped generated booking IDs and actual checkout paths in router/integration tests. Browser/device acceptance must confirm rendered remote media and session lifecycle; passing a build or receiving credentials is insufficient. Cover supported Android/iOS and mobile/desktop browsers, with a declared support matrix and a clear unsupported-browser fallback. Obtain authorized test transactions/recipients before exercising paid or email flows; do not message real customers during implementation verification.

## 6. Release and rollback plan

1. Capture deployed Worker, consumer, website and Android revisions/config; the prior audit confirmed flags but did not prove deployed backend parity or successful media.
2. Deliver backward-compatible API/data changes before clients that depend on them. Any migrations are additive and environment-specific; never copy staging data or flags to production. Test integrated journeys in an explicitly selected test environment before the production smoke run.
3. Stage a reviewable release set containing only journey fixes. Verify deployment/build requests against project rules at execution time; this plan itself dispatches nothing. All builds run through GitHub Actions; deploy Workers only through the mandated wrapper with production authorization.
4. After explicit production approval, perform necessary migrations/deployments in dependency order, distribute the corrected app through the requested release flow, then run the authorized real-session acceptance matrix. Verify app version and website/API revisions used in the evidence.
5. Roll back clients/services compatibly if acceptance fails. Preserve orders and entitlements, pause only the affected capability with explicit production authorization, keep purchase recovery accessible, and communicate a truthful temporary-unavailable state. Do not destroy bookings or redirect paid users to an unmetered legacy room.

## 7. Definition of complete

All acceptance rows pass with recorded release IDs, non-secret session references, email provider delivery status and remote-media evidence. There are no placeholder start buttons, past-first appointment selection, lost app-link IDs or promises of email delivery without evidence. The existing sidebar is sufficient for both parties to find their work/purchases, start the right camera session and join from app or browser. Existing purchases remain valid. Graphiti and the audit checklist record observed results and residual limitations. Features such as recordings, replay and session extensions remain separate scope unless requested; this plan preserves existing pricing, cancellation, metering and settlement policies.
